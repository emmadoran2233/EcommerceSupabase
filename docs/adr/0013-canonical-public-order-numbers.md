# ADR 0013: Canonical public order numbers

## Status

Accepted

## Context

`orders.id` is a compact bigint primary key used by order items, payments,
fulfillments, and Edge Functions. Exposing that sequential database key to users
is hard to read safely and couples public contracts to storage. The legacy
`orders.order_id` field is also overloaded and cannot be trusted as the canonical
identifier.

## Decision

Keep `orders.id` as the internal relational key and add an immutable, unique,
customer-facing `orders.order_number` generated by PostgreSQL.

The format is:

```text
YYYYMMDDHH24MISS-SHORTID-INTEGER
20260921214530-ABCDEF-00000123
```

- The timestamp is the order creation time in UTC.
- `SHORTID` is six uppercase hexadecimal characters of entropy.
- `INTEGER` is the zero-padded internal order sequence and expands beyond eight
  digits when required.
- The full value is protected by a unique index and cannot be changed after
  assignment.

The database generates the number for both new and backfilled orders. Customer
pages, admin pages, email subjects, support lookup, status lookup, and shipping
provider metadata use the public number. Internal foreign keys and trusted Edge
Function operations continue to use the bigint key.

## Consequences

- Existing foreign keys do not need a high-risk rewrite.
- Public order references are recognizable, sortable by creation time, and
  difficult to guess from the integer sequence alone.
- Database migrations must be deployed before Edge Functions that select
  `order_number`.
- `orders.order_id` remains temporarily for compatibility and can be removed
  only after the legacy-contract readiness report and a code-reference audit are
  clean.
